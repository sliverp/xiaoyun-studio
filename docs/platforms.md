# 多平台推流与弹幕

小云 Studio 将一个“平台连接”作为配置单元：选择平台，填写推流地址/密钥与直播间，再连接弹幕或扫码。每个连接都有独立的推流状态、弹幕状态和后台登录目录。同一平台可添加多个连接，合计最多 8 个。

## 统一操作

在「平台与推流」点「＋ 添加平台」，选择哔哩哔哩、抖音、快手或视频号。填写：

- 平台连接名称：用于区分账号和场次。
- RTMP/RTMPS 服务器地址与推流密钥：使用平台直播后台提供的值；这里不使用 RTSP。
- 直播间地址或 ID：弹幕来自这个房间。视频号使用视频号助手的直播后台，不需要填公开房间号。
- 参与同时推流：勾选后，点击全局输出按钮会一起启动；也可以在单张卡上单独启停。

「连接弹幕」打开该房间的服务器浏览器并监听消息；「扫码登录」在同一连接的浏览器里显示官方登录页面。登录成功后有房间地址的连接会返回房间。登录态仅留在服务器的该连接目录中，不要求手工复制 Cookie。登录页面、二维码刷新和允许的登录控件都可从导播台查看和操作。

**连接弹幕不会隐式开始推流，推流成功也不等于弹幕已经收到。** “页面已打开，等待真实弹幕”表示后台浏览器已连接但尚无实际可解码内容。“正在接收真实直播数据”必须有真实弹幕或指标输入。平台要求安全验证、房间未开播、昵称被匿名化、加密或协议不支持时，会保留相应提示，不生成模拟观众。

也可添加「自定义 RTMP」，用于其他平台或旧版本迁移配置。它不内置弹幕浏览器；外部弹幕桥仍可使用受保护的接入口。

## 调研与采用方式

调研日期：2026 年 10 月 27 日。以下链接均为项目维护者或平台的一手资料。

| 平台 | 相关开源/官方方案 | 本项目采用方式 |
| --- | --- | --- |
| 哔哩哔哩 | [blivedm](https://github.com/xfgryujk/blivedm) 同时覆盖 Web 与官方开放平台；新版 [bilibili-live-ws](https://github.com/simon300000/bilibili-live-ws) 只接受开放平台返回的长连参数 | 官方直播网页建立自己的连接，服务器被动读取其 WebSocket，解析长度头、JSON、zlib/Brotli 消息；完整用户信息依平台登录与实际返回 |
| 抖音 | [DyHub](https://github.com/ymstar/dyhub) 有浏览器/CDP 和直连两类采集路径 | 采用浏览器/CDP 思路，让官方网页完成登录与连接签名，只解码收到的 Protobuf/gzip 消息；不引入其独立签名资源 |
| 快手 | [kuaishou-live-mate](https://github.com/atvkh/kuaishou-live-mate) 展示 WebSocket 拦截与 Protobuf 解析 | 被动解码官方直播网页的消息，只接收弹幕和实际指标；不加入自动发送、点赞或关注行为 |
| 视频号 | [wxlivespy](https://github.com/fire4nt/wxlivespy) 展示读取视频号助手直播消息的原理 | 复用本项目已实现的助手后台响应采集器，按平台连接隔离登录目录 |

本项目没有将某个第三方完整采集器直接嵌入运行。运行依赖增加了维护中的 protobufjs，用于有限的 Protobuf 字段解码。具体字段、源文件和许可说明见 [弹幕解析来源](platform-chat-sources.md)。浏览器建立连接的方案减少了自建签名代码，但仍依赖平台网页和非公开消息协议，平台调整后需要更新适配器。

B 站还有[官方直播开放平台](https://open-live.bilibili.com/)，需按其文档申请开发者接入与主播授权；它不是“只填房间号即可使用”的通用匿名接口。快手的[直播开放平台](https://openlive.kuaishou.com/)也提供合作接入能力。需要稳定商业集成时，可在当前统一连接接口后增加相应官方授权适配器；本版本不冒充已经取得这些平台的应用资质。

## Linux 后台扫码能否使用

本项目的采集浏览器运行在服务器，不是操作者电脑上。二维码是官方页面在服务器 Chromium 中真实渲染的内容，经受保护的截图接口显示给控制台；手机扫码确认后，会话写入服务器该连接的浏览器目录。控制台页面关闭后，已运行的采集浏览器仍由服务管理。

这条链路在机制上不依赖桌面或前台 Chrome，Linux 镜像也具备 Chromium。**能打开登录页/看到二维码，与账号已经成功登录并收到直播弹幕是不同的验收项。** 平台可能对服务器出口 IP、地区、设备、账号权限或安全验证提出额外要求，不能承诺每个账号在任意云服务器都能直接通过。

建议在正式使用的 Linux 主机分别验收：打开官方登录页、手机扫码、确认登录态、进入正在直播的房间、发一条本人测试弹幕、在卡片看到消息计数增长，再确认 AI 收到的来源正确。没有当前直播账号时，自动测试只验证协议样本、隔离生命周期和真实页面可达情况，不能替代这一步。

## 多路输出与故障隔离

服务器只进行一次 H.264/AAC 编码，将同一媒体送入每个平台独立的 RTMP 发送进程。每路都有有界缓冲、实际发送进度、错误、停止和重试状态。本地 MP4 录制独立运行。一条目的地断开时，其他目的地和录像继续，不需要整个直播重新开始。

“正在编码”表示媒体引擎工作，“正在推流”以对应平台发送进度为依据；平台能否对外展示，还需在平台后台确认。推流密钥只在服务器端使用，状态接口只显示是否已保存。输出时修改某路地址/密钥需先停止该路；全局分辨率、帧率和编码参数需停止全局输出后修改。

出网带宽按输出路数累加；同码率四路推流大致需要单路四倍的出网带宽。视频编码只做一次，每路的转封装仍有少量资源消耗。实际性能应在目标服务器测量。

## AI 与报告中的来源

弹幕保留平台、连接名称和独立消息 ID，不同平台恰好出现相同消息 ID 不会相互去重。AI 仍只查看最近两分钟、最多 100 条新弹幕，可以概括共同话题或点名回应，并知道消息来自哪里。

在线人数、观看人数、热度、点赞等按连接分别保存与注入模型，不把不同平台的热度单位混加，也不把不同时间的在线峰值相加。CSV 每个切面附带 connectionId、platform 和 connectionName；JSON/Markdown 分平台列出峰值。指标缺失时保持缺失。

使用平台弹幕与登录功能需要操作者拥有账号和相应权限。这里不绕过验证码、账号限制或平台开播授权；扫码登录不等于平台已经创建直播或开放第三方 RTMP 推流。
